## 1. 影视选集：显示的集号和实际播的对不上

### 现象

用户报「凡人修仙传 年番4，选第 197 集播放的是 124 集，第一集播放的是 125 集」。

### 根因

**不是播放错，是显示编号错。**

把源给的选集列表完整导出后真相很清楚 —— 这个源的 199 集里塞了**两套互不连续的编号体系**：

```
下标 0   = [3.2GB]125.mp4     → 实际第 125 集
下标 72  = 197.mp4            → 实际第 197 集
下标 73  = S01E01.mp4         → 又从第 1 集重新编号
下标 196 = S01E124.mp4        → 实际第 124 集
下标 198 = S01E126.mp4        → 实际第 126 集
```

详情页原来拿「列表位置 + 1」当集号显示，所以界面上写「第 197 集」，实际内容是 `S01E124.mp4` —— 和用户描述逐字吻合。播放侧按源下标取，是**对的**；错的是显示。

### 改法

新增 `desk/widget/EpisodeNumber.java`，从集名里解析真实集号：

- `S01E24` / `S02E07` → 取 E 后的数
- `第24集` / `第24话` → 24
- `EP07` / `E24` → 7 / 24
- `125.mp4` / `189.mp3` → 文件名主体里的数字
- 解析不出来才退回「位置 + 1」；名字本身不是编号（「开端」）就原样显示

`DetailPage.episodeLabel()` 用它显示，`DetailPage.chunkLabel()` 让分段条标签也用真实集号（原来写死「1-32」，和格子里显示的号对不上）。

### 踩过的两个坑（都记在代码注释里）

1. **`[3.2GB]125.mp4` 里的体积被当成集号**：扩展名正则要求纯字母时，`3.2GB` 匹配成「3 的 .2GB 扩展名」，集号变成 3。
   改成「扩展名首位必须是字母」——`mp3` 的首位是 m，`2GB` 的首位是 2，天然分开。
2. **`189.mp3` 被漏掉**：扩展名要求纯字母时 `mp3`（首位 m）能过，但 `m4a`/`x265` 这类要放宽；放宽后又会让 `2GB` 混进来。最终规则是「首位字母 + 其余可数字」。

本机写了 17 个真实样本的用例验证（含 `[3.2GB]125.mp4`、`[2.6GB]189.mp3`、`S01E124.mp4`、`第24集`、`EP07`、`001.m4a`），全部通过。

### 实测

```
界面上显示：177 178 179 … 193 | 189 190 191 192 193 194 195 196 197
源原始顺序：177.mkv … 193.mkv | 189.mp3 190.mp3 … 197.mp4
```

点「193」→ 源 index 16 = `193.mkv` → 播放器收到 `idx=16 集名=[4.4GB]193.mkv`。**显示与播放完全一致。**

## 2. B站 / 应用模块向下翻页跳左上角

### 根因

`PageGridView` 记住「用户最后站在哪张卡」，靠重排后把焦点还回去。但 `onGlobalFocusChanged` 里有一条：

```java
} else if (newFocus != this) {
    keepPosition = -1;   // 焦点去了别处 → 清掉位置
}
```

翻页加载下一批时，带焦点的卡被回收 → 系统把焦点交给窗口里第一个可聚焦控件（左上角模块胶囊）→ **这一刻焦点离开了墙，`keepPosition` 被清成 -1** → 后面再补焦也补不回来了。

### 改法

- 焦点离开墙时**不再清位置**，改记一个 `userLeftWall` 标记，区分「用户主动按了键离开」和「系统回收导致」
- 目标卡那一帧还没挂上来时（列表正在重排），**下一帧再试**，不直接放弃
- 页面层提供 `markUserLeft()` / `markUserEntered()`：用户主动往页签走时调前者，焦点送回墙里时调后者

B 站、应用、音乐三页都接了。实测翻 8 次焦点稳定在 `bili_grid[12/16]` / `apps_grid[6/10]`，不再跳左上角。

## 3. 音乐模块

### 3.1 「播放全部」按上键应到右上角「正在播放」

两处问题：

1. **上键路由错了**：`handleKeyDown` 里 `playAllBtn.hasFocus()` 走的是 `focusChip()`（顶栏页签）。改成跳右上角 `music_now_chip`。
2. **「播放全部」在遥控器上根本到不了**：它和标题同一行，按几何搜索焦点会直奔更近的顶栏页签。在 UP 路由里显式给它焦点（内容已在顶部时）。

实测：卡片墙 → UP → 「播放全部」→ UP → 「正在播放」胶囊。

### 3.2 播放页上一首 / 下一首无反应

四个独立缺陷叠在一起，逐个查出来的：

| # | 现象 | 根因 | 改法 |
|---|---|---|---|
| a | 焦点跑到底部播放条上 | 播放页打开时 `bar`（底部播放条）仍 VISIBLE，两个控件层叠着抢焦点 | 开播放页时把 `bar` 藏起来（`updateBar` 里也改成 `stageOpen ? GONE : VISIBLE`） |
| b | 焦点永远走不出「暂停」 | `stageToggle` 的 `OnKeyListener` 抢左右键当快退快进 | 整个 `OnKeyListener` 去掉，左右键交回焦点导航（遥控器本来就有专门的快退键） |
| c | 控制区收起后右键被吞 | `dispatchKeyEvent` 在控制区收起时把左右键当快进 | 左右键不再在那里当快进，收起时第一下先唤回控制区，第二下才走位 |
| d | **切歌函数被调用但不切** | `queue` 是空的 | 见下 |

**d 是最隐蔽的一个**：播放队列只有 `buildTrackRows` 会填，而在线榜单 / 歌单 / 「我的」这些页面走的是另一条路（直接往 `rows` 里塞卡片）。结果歌在放、`nowPlaying` 有值，但队列是空的，`advanceQueue` 一看就 return。

日志实证：`下一首 queue=0 idx=0` → 修完：`下一首 queue=32 idx=0`，切歌正常。

改法：新增 `rebuildQueue()`，在 `rebuildRows()` 末尾**统一**按当前 rows 重建队列（不管当前是列表还是卡片墙）。正在放的那首用身份重新定位，定位不到就插到队首。

实测：播放页内「下一首」换到新链接，「上一首」回到队列里的前一首。

## 4. 应用模块：图标 + 自定义顺序

### 图标

继续沿用上一轮从 Aerial TV 移植的 `AppIconArt`（连续圆角 + 同色渐变底板 + 上沿高光），实测清晰度已达标，本轮未再改动图标合成。

### 自定义顺序

- 给了「我的排序」出口：清掉自定义、回到默认排序（没有这个出口就再也回不去了）

实测：长按「乱炖直播」→ 移到最前 → 重启 App 仍在第一位。

## 6. 其它模块带筛选时按 OK 显示筛选

### 根因（比界面问题更深）

界面侧根本没机会弹筛选 —— **类目里的筛选条件在解析阶段就被整个丢掉了**。

实测数据：源一直带着 filters（花卷高帧 3 个维度、花卷电影/剧集各 6 个、花卷动漫 5 个），但我们的解析只取了类目 id 和名字，`filters` 永远是空数组。

### 改法

1. **`SourceFeed` 补上筛选解析**：类目 JSON 顶层有 `filters`（key 是类目 id，值是该类目的筛选维度列表），按 TVBox 原版的结构解析后**按 id 分发**到各个 `SortData` 上
2. 新增 `desk/SortFilterDialog.java` + `layout/dialog_sort_filter.xml`：每行一个维度（年份 / 字母 / 排序），行内横排可选值
3. 顶栏项点击：有 filters 就先弹筛选，没有才直接进类目
4. 「确定」应用并重新拉列表；「重置」清空；「取消」不改动

交互上参照 TVBox 的行为：再点一次已选中的值 = 取消这一项。

> 电视上多一颗筛选图标就多一次按键，还跟类目名挤在一排里认不出来 —— 所以做成「按确定直接弹」。

实测：花卷高帧 → 按确定 → 弹出「年份 / 字母 / 排序」三个维度 → 选 2026 → 确定 → 列表重载（带上了 4K HDR / 60帧等清晰度标注，说明确实按条件取回了不同结果）。

# 追加（10/25 晚 19:25 重新打包）：顶栏左右移动不再被拽进内容区

## 问题

用户在顶栏（首页 / 收藏 / 类目…）按左右键逛页签时，焦点会自动跳到下面的内容区里，打断操作。

## 根因

`PageGridView` 的补焦逻辑：每次布局时如果「墙里没焦点、但记住了位置」，就把焦点抢回那张卡。
`keepPosition` 只在「用户自己走了」（`markUserLeft`）时才清 —— 但这个标记只有
B 站 / 应用 / 音乐三个页面在焦点上顶栏时调用；**桌面顶栏（首页 / 收藏 / 类目）这条
路从来没人通知墙**。于是：焦点从卡上到顶栏 → 按左右换页签 → 内容重载重排 →
墙把焦点从页签上拽回卡里。每换一页抢一次，顶栏根本没法逛。

## 修法（`PageGridView.onGlobalFocusChanged`）

用「焦点出发的那张卡还挂不挂在墙上」区分两种离开：

- **用户走出去**：oldFocus 还挂在墙上（方向键从卡导航到顶栏/页签）→
  清掉 keepPosition，不再抢回。
- **系统甩出来**：oldFocus 已被回收（翻页加载、重排）→ 照旧留位置补焦，
  翻页时焦点不会跳左上角（上一轮修的问题不回退）。

## 实测

- 顶栏从「首页」连按右穿过 5 个类目页签，焦点全程留在顶栏，内容跟着切
- 从顶栏按 DOWN 正常回到内容；DOWN 翻 6 行焦点稳定在卡上（翻页补焦不回退）
- UP → DOWN 往返自然；0 崩溃

# 追加（10/25 晚 19:29 重新打包）：搜索页往右不再丢焦点

## 问题

搜索界面按右键（从键盘区往结果区走），焦点丢失，选不中搜到的内容。

## 根因

结果墙是 `PageGridView`（继承 GridView）。AbsListView 构造时把**容器自己**设成了
可聚焦，于是它也成了焦点候选——而且容器的矩形比里面的卡更靠外，几何搜索常常是它赢：
按右键焦点落在结果墙这个「空壳」上，什么都不高亮、按确定没反应，看起来就是焦点丢了。

## 修法

`PageGridView` 构造时 `setFocusable(false)`：墙本身不参与焦点搜索，焦点只落在
卡上。墙的补焦、翻页走的都是 `child.requestFocus()`，不依赖容器可聚焦，所以
B 站 / 应用 / 音乐 / 桌面各墙的行为不受影响（全局生效，顺带让所有墙从旁边
控件按方向键进入时都直接落到卡上）。

## 实测

- 键盘「搜索」按钮按右 → 直接落到结果卡（不再落空壳）

# 追加（10/25 晚，仍未打包）：B站/应用翻行闪左上角修复

## 问题

B 站和应用模块下翻：屏幕两行内容，焦点到第二行再往下翻，焦点跳左上角再马上回来（闪一下）。

## 根因

平滑翻行 220ms 是一帧一帧走的，旧焦点卡滚出视口被 GridView 回收 ——
系统立刻把焦点甩给窗口里第一个可聚焦控件（左上角模块胶囊），高亮先渲染了；
等下一帧布局 `restoreFocus()` 才把焦点补回来。补焦本身没坏，**晚了一帧以上**。

## 修法

`PageGridView.onGlobalFocusChanged` 的回收分支里**同步**把焦点按回墙内：
立刻抓住挂载卡里离原位置最近的一张 `requestFocus`（新增 `nearestAttachedChild`）。
焦点变化回调发生在绘制之前，所以左上角的高亮一帧都没渲染过；
滚动停稳后页面自己的补焦再把焦点放到该去的那格，位置不受影响。

# 追加（10/26 晚，未打包）：应用磁贴裁切真因修复 + 米家/应用商店补齐 + 顶栏左右对称

## 磁贴「放大过多 / 裁切」的真因（本轮终于修对）

之前一直以为是取图源不对，其实是 `AppTileArt.fromBanner()` 里一处几何错误：

```java
Bitmap back = layer(...);   // layer() 固定生成 352×198 的画布
cover(canvas, banner, w, h, sw, sh);  // 但 w×h 是按横幅算的，比如 640×360
```

横幅被按「自己的尺寸」画进一张 **352×198 的小画布**，于是只画进去左上角一块 ——
屏幕上看到的就是「放大过多 + 右边和下边被裁」。逐应用看日志：

| 应用 | 横幅原图 | 原来被塞进的画布 | 现象 |
|---|---|---|---|
| SmartTube / 月光 / MD3Music | 640×360 | 352×198 | 右边的字被切 |
| TVBox / 影视仓 / 应用管家 | 1280×720 | 352×198 | 只看到左上角 |
| 天微影视 | 858×432 | 352×198 | 底部「TianWei」被切 |
| BT | 2560×1440 | 352×198 | 大logo糊成一块 |

修法：画布按横幅自己的尺寸建（最多两倍磁贴宽 704×396），`cover()` 用 intrinsic
尺寸做等比铺满；不是 BitmapDrawable 的（LayerDrawable / AdaptiveIconDrawable）
也用 intrinsic，不再退回磁贴尺寸。这跟 Aerial 的 `fromBanner/createBitmap(w,h)`
是一致的。

## 米家 / 应用商店 不显示

应用列表只查 `CATEGORY_LAUNCHER` + `LEANBACK_LAUNCHER`，这两个包一个都没有：

- **应用商店**（`com.xiaomi.mitv.appstore`）只声明 `CATEGORY_APPSTORE_LAUNCHER`
- **米家**（`com.xiaomi.smarthome.tv`）连启动类目都不声明，只有 MAIN + DEFAULT

照搬 Aerial 的 `AppCatalog`：补查 `APPSTORE_LAUNCHER` 类目，并按组件写死

# 追加（10/26 晚，未打包）：系统应用磁贴残留背景 + 背景不再跟图标变色

## 磁贴「残留背景」（高清播放器 / 电视设置 / 电视管家）

背景更花。现在这个方法只负责把氛围层收起（alpha → 0），页面固定用默认背景，

# 追加（10/30 晚，未打包）：播放器快进卡顿 / 音画不同步优化

## 现象

播放中按左右键快进，画面卡一下，之后音画对不上（声音跑在画面前面），
要等一会儿才自己纠回来。影视仓 / OK影视 这些同样的 TVBox 内核没有这个问题。

## 根因（两条，叠在一起）

1. **seek 落点是「精确位置」**。ExoPlayer 默认 `SeekParameters.DEFAULT`
   （toleranceBefore/After = 0）：它必须从目标<b>前面那个关键帧</b>开始，
   把中间每一帧都解码出来再丢掉。电视 SoC 上这段要几百毫秒 —— 用户看到的就是
   「快进后卡一下」；而音频不用等这一步，包一到就出声，于是音画错开几百毫秒。

2. **回缓冲门槛太高**。我们给 LoadControl 传的是 ExoPlayer 的默认值
   （min/max 50s、起播 2.5s、回缓冲 5s）。seek 之后播放器重新进 BUFFERING，
   按 2.5 秒的缓冲门槛才恢复出画 —— 这就是「卡一下」的另一半。

## 改法

- `ExoPlayer.initPlayer()` 里设 `SeekParameters.CLOSEST_SYNC`：直接跳到离目标
  最近的关键帧，不解码-丢弃，视频立刻有画面，音视频从同一点起跑，
  卡顿和音画不同步一起消失。
- `DefaultLoadControl` 改成 15s/30s、起播 1s、回缓冲 2s，32MB 字节上限，
  `setPrioritizeTimeOverSizeThresholds(true)`（码率高时不因为字节上限提前停缓冲）。
- `MyVideoView.seekTo()` 之后 700ms 按**实际落点**再对齐一次弹幕：落点可能和
  请求位置差半秒到一两秒，不重对的话弹幕会比画面早/晚半句。

## 取舍

落点会吸附到关键帧，和「想要的位置」最多差一个 GOP（这类片源一般 1~2 秒）。
这是电视播放器的通行做法（TVBox / FongMi 内核也是这么配的）。如果更在意
「跳得准」而不是「跳得快」，把那一行换成 `SeekParameters.DEFAULT` 即可回退。

## 验证状态

改动编译通过（`BUILD SUCCESSFUL`）。**电视当时离线**，机上验证待补：
装包后播放 1080P 片源连续快进 5 次以上，看两件事 ——
① 快进后是否还有明显停顿；② 停顿后音画是否还错开。
日志里搜 `echo-exo-seek-closest-sync` 可确认新参数已生效。


### 机上验证（MiTV-MFTR0，10/30 20:47）

装包 → 详情页「百度原画#01」4K HEVC 片源起播：

- 日志 `echo-exo-seek-closest-sync` 已打印 → 新参数生效
- 单次快进：画面直接跳到新位置（片头字幕 → 鱼缸场景），连拍 6 帧全部有画面，
  **没有黑屏、没有加载圈**
- 连按 6 次快进（模拟连点）：仍正常播放并出字幕，0 崩溃
- 顺带确认：`echo-exo-disable-async-codec-queue` 这次真的生效了（2.19 有这个 API），
  它是「强制同步出队」的开关 —— 如果音频仍比画面快，下一步就从这个开关下手

音画是否对齐最终得靠耳朵判断，这一项等用户实听反馈。

# 追加（10/30 晚，未打包）：应用页三修（顶栏压住磁贴 / 焦点飞出边界 / 翻页卡顿）

## 1. 磁贴压在顶栏上

卡片墙为了「聚焦放大的卡能溢出格子」关掉了 `clipChildren`。GridView 一旦滚动，
上一排的卡就画到内容区以外、直接盖住顶栏胶囊（截图里胶囊整个被吃掉）。

修法：内容层上面加两条**压暗罩**（上面 94dp 实心 `desk_bg`，下面 26dp 渐隐），
并把「模块胶囊 + 页签胶囊」改到压暗罩之后声明 —— FrameLayout 按子节点顺序绘制，
顺序就是层级。

## 2. 焦点飞出边界（本轮的真问题）

最左一列再按左，焦点直接飞到左上角的模块胶囊，得按右才回来。
根因是 GridView 不认边界：几何寻焦在墙里找不到更近的卡，就摸到屏幕左上角去了。

修法：`PageGridView.atHorizontalEdge()` + 各页 `dispatchKeyEvent` 里到边就地吃掉
（应用 / B 站 / 音乐 / 信号源）。搜索页和详情页的选集格**不拦**——
它们左边就是键盘 / 线路条，拦了会把人困住。

（顺带记一笔：一开始把拦截写进 `PageGridView.dispatchKeyEvent`，实测不生效 ——
按键是顺着焦点链走的，到边那一下墙已经被跳过了，只有页面层拦得住。）

## 3. 翻页卡顿 —— 两个实打实的性能 bug

**（a）磁贴缓存等于没开。** `LruCache<String, Bitmap>(80)` 的容量单位是
`sizeOf()` 的返回值（字节），写 80 就是「整个缓存 80 字节」，一块横幅磁贴
1.1MB —— 每次绑定都击不中，重新解码图标 + 重新合成几十毫秒。改成 32MB，
再给 `AppTileView.setTile/setName` 加同值跳过（避免重复上传纹理）。

**（b）全屏背景每帧重画径向渐变。** `BackdropView` 每帧画三层全屏渐变
（两道光都是 RadialGradient）。`dumpsys gfxinfo` 实测：GPU 单帧 20~25ms。
改成 `onSizeChanged` 时画进一张位图，之后每帧只贴图。

### 实测（MiTV-MFTR0，同一段翻页操作）

| 指标 | 改前 | 改后 |
|---|---|---|
| Janky frames | 29~34% | **8.9~11%** |
| 中位帧耗时 | 36~38ms | **17ms** |
| GPU 单帧 | 20~25ms | **11ms** |

- 应用页滚动时顶栏干净，胶囊清晰，磁贴不再透出
- 最左列按左不动；最右列按右不动；B 站同样生效
- 从网格按上回页签、按下进网格都正常；0 崩溃

# 补充（10-31 ~ 11-01）：返回桌面落点、胶囊底板、断点续播

## 1. 返回桌面时焦点落在「开始播放」

**现象**：从首页 Hero 的「开始播放」进详情（或经搜索进详情），一路退出回到桌面，
焦点停在那颗白底的「开始播放」上，看着像还没开始播。

**根因**：页面栈入栈时记「来处」= 当时获得焦点的那颗按钮，出栈就原样还回去。
Hero 上这三颗（开始播放 / 收藏 / 详情）不是「一格内容」，而是打开下一层的扳机，
把焦点还给它们等于让人以为要再按一次。

**改法**：`DeskActivity.isHeroAction()` 判 `hero_actions` 整棵子树；是它就直接弃用这个来处，
回落到默认落点「桌面」胶囊。从海报、观看历史海报进去的仍然回到原来那张卡。

## 2. 「桌面」胶囊的底板像一块残留

**根因**：胶囊底板不是实时模糊，是按自己在窗口里的位置去一张静态磨砂小图上取样。
两处会让它取错：模块页盖着时胶囊是 `GONE`，回来第一帧 `getLocationInWindow` 还是 `(0,0)`，
代码退化成画一块**纯色**；而 View 画完不会自己重画，那块纯色就永久留在顶栏。
另外模块页期间磨砂图不重拍，回来时取样还是旧图。

**改法**：
- `GlassDrawable` 记住上一次有效位置，取不到时沿用，不再画纯色块；
- `DeskActivity.invalidateGlassSoon()`：顶栏「藏过再显示」（回桌面、退出沉浸）后补一帧重绘；
- `refreshDeskGlassLater()`：回桌面 380ms（等 Hero crossfade 走完）重拍磨砂图。

## 3. 断点续播

**现象**：从观看历史点回来永远从第 1 集、第 0 秒开始。

**根因**：详情页只往自研的 `VodHistory`（片名/海报）记了一笔，没碰内核那张 `vodRecord` 表，
所以「看到哪条线路第几集」根本没有落盘。

**改法**：
- 起播时 `RoomDataManger.insertVodRecord(sourceKey, info)`，把 `playFlag/playIndex` 写进去；
- 详情加载后 `getVodInfo` 读回来并夹到集数范围内（源站删过集不会越界），`applyResume()` 应用；
- 一集之内的秒数不另存：播放器进度键就是 `源+id+线路+集数+集名`，
  退出时 `VideoView.saveProgress()` 落盘、起播时 `getSavedProgress()` 自动 seek。

**实测**：播到 S01E03 的 00:23 退出 → 回桌面 → 再从观看历史进详情 →「开始播放」
直接是 S01E03，从 00:23 续上。

## 4. 退出播放器回详情页，焦点落在正在看的那一集

以前一律还给「开始播放」（看着像要重头再来）。新增 `DetailPage.focusPlayingEpisode()`，
按 `playIndex - chunkStart - firstVisiblePosition` 换算出格位再请求焦点，找不到才回落默认落点。
