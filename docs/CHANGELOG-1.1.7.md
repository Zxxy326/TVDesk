# TVDesk 1.1.7

版本：1.1.7（versionCode 18）
日期：2026-11-06

主题：**背景墙改造** —— 冷启动时的静态海报换成「影视 + B 站热门」混合队列，
有视频的条目静音播 8 秒再切下一条。按《TVDesk 高清背景与视频轮播实施方案》落地。

---

## 一、背景队列（方案第 4 节）

### 独立条目模型

新增 `core/bg/BackdropItem`：来源类型（影视 / B 站）、稳定键、展示载体、横图与竖图、
B 站 bvid/cid/时长、原图像素。「影视条目」和「B 站条目」不共用字段，
B 站的 bvid 不会被当成影视源的内容 id——这一点以前会出问题：
拿 bvid 去影视源里搜，等于搜一部不存在的片子。

### 队列规则

新增 `core/bg/BackdropQueue`：

| 规则 | 实现 |
|---|---|
| 影视 / B 站比例 | 默认 70 / 30，某一池不够时用另一池补满，不留空位 |
| 队列长度 | 一轮 14 条（8 秒一条约两分钟） |
| 去重 | 影视按 `源 key + 内容 id`（缺失退回片名），B 站按 bvid |
| 每轮洗牌 | `Collections.shuffle`，一轮内不重复 |
| 跨轮不连播 | 新一轮首条与上一轮末条相同时，和第二条对调 |
| 独立于海报行 | 队列吃**截断前**的完整列表（海报行有 `ROW_LIMIT`，背景没有） |

### B 站热门

新增 `core/bg/BiliBackdropSource`：走既有的 `BiliClient.popular`（综合热门，不用排行榜
冒充），45 分钟缓存，失败保留上一批。换背景不触发重新拉榜——沉浸态 8 秒切一条，
每次都问接口既浪费也容易被风控。

**只取 DASH 的视频轨**（`dashVideo`），不合并音轨：背景永远无声，省一次合并、
也省掉音轨的带宽。

## 二、动态背景播放器（方案第 5 节）

新增 `desk/BackgroundWall`：一个独立的、静音的、无控制栏的 ExoPlayer 实例。

- **只在沉浸态启动**。正常浏览时按钮和海报行都在，反复切视频流没有意义。
- **SurfaceView** 放在布局最底层，静态图盖在它上面；**收到首帧才淡出静态图**，
  准备期间用户看的是图，不是黑屏。
- **8 秒从首帧之后算**，取流和缓冲时间不吞掉预览时长；片段比 8 秒短就播完即切
  （`STATE_ENDED`），不循环补足。
- **首帧 3 秒超时**回静态图，不让队列卡在一条取不到流的视频上。
- **不申请音频焦点**：音量固定 0，且根本没有音轨，不会打断正在放的音乐。
- **代次（generation）**：每次换条自增，迟到的取流回调、首帧回调只有代次对得上
  才允许动画面。8 秒一条的节奏下，取流慢一点就会撞上「已经切到下一条了」。
- **资源互斥**：进前台视频（影视 / B 站 / 直播）、退出沉浸、`onPause`、`onDestroy`
  全部 `stop()`；只 pause 不会释放 MediaCodec，前台再开 4K 就是两个硬解实例抢资源。

## 三、点击与当前背景一致（方案第 4.9 条）

- 沉浸态轮到 B 站条目时，Hero 的标题 / 徽章（「B站热门」）/ 简介（UP 主 · 时长）
  全部来自那一条，三颗按钮里的播放和详情分流到 `BiliDetailPage`。
- 收藏那颗心对 B 站条目隐藏：本机收藏清单只存影视，收了也点不回来。
- **退出沉浸时不强行换回影视条目**。用户看到的画面就是那一条，一退出就把标题换掉，
  刚才那下「开播放」会打开另一部片子。用户按方向键进海报行时，
  `onPosterFocused` 自然把 Hero 换回影视。
- 沉浸态圆点改为跟队列走（一轮的条数），不再跟海报行；退出到 B 站条目时收起来。

## 四、图片加载

- Hero 背景**按这块屏的真实像素解码**（`DisplayMetrics`），不再写死 1920×1080：
  1080p UI 解 1080p，4K UI 跟着涨。既不会在 4K 上糊，也不会无条件按原图解码
  把一张 8K 剧照的几十兆内存吃进去。
- 磁盘缓存与内存缓存沿用 Glide 的默认策略。

## 五、设置

「桌面」页新增两项：

- **动态背景**（默认开）：关掉就只轮播静态图，连热门列表都不拉，老盒子省功耗。
- **背景只要 4K**（默认关）：打开后视频只接受 2160p 轨道，拿不到就回静态图，
  不拿 1080p 顶上去冒充。

---

## 六、与方案的差异（需要知道）

1. **严格 4K 只约束视频轨道，图片不做像素过滤。** 方案第 3.4 节要求图片也满足
   原始像素，但抽样 20 张热门封面 0 张达到 3840×2160；如果连图片一起卡，
   严格模式下桌面会几乎没有背景可放。这一版先只卡视频，等有真实 4K 素材再说。
2. **不做 `MediaCodecList` 能力预检。** 当前只依赖「轨道实际宽高」这一个事实
   （`player.getVideoFormat()` 回填并打日志），设备能力不足时由播放器自己报错，
   走首帧超时回静态图。
3. **不做 clipStartMs 随机起点**：在线预览从 0 秒开始（方案第 5 节的首期约定）。

## 七、尚未验证

电视当时不在线，以下项**没有真机结论**，需要开电视后逐项过：

- 3840×2160 的实际 Surface 输出与硬解（本机 UI 是 1080p，首期按 1080p 验收）。
- B 站未登录 / 普通登录下实际能拿到哪一档（接口返回的 `accept_quality` 不作数）。
- 首帧 P50/P95、连续 30 分钟 / 100 次切换的内存与温度。
- 与抖音、音乐播放器的互斥（代码里已加，但没跑过真机）。
